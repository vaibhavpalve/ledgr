# ADR-004: Envelope encryption key hierarchy for document/attachment storage

- **Status**: Accepted
- **Date**: 2026-08-21

## Context

SEC-022 requires "envelope encryption with a managed KMS/HSM; per-tenant data encryption keys
wrapped by a key-encryption key." IAM-004 requires "a per-tenant encryption key... used for
document and attachment storage, so a key revocation isolates one tenant." SEC-023 requires
"automatic key rotation at least annually, with re-wrapping and no downtime" plus a documented,
tested emergency rotation procedure. CLAUDE.md's confirmed stack names Azure Key Vault / managed
HSM as the KMS and Azure Blob as document storage.

The design question this ADR answers: what, precisely, is a "tenant" for encryption purposes, how
many keys exist and at what layers, and how does rotation — both routine and emergency — actually
work without either re-encrypting every stored document or leaving old key material live
indefinitely.

## Decision

### Key hierarchy

```
KMS-held KEK (Azure Key Vault, HSM-backed RSA key — never leaves the vault)
  -- wraps -->  one DEK per ADMINISTRATION (administration_encryption_key, versioned)
       -- encrypts -->  individual document/attachment bytes (AES-256-GCM)
```

Three layers, three different lifetimes:

1. **KEK** — one system-wide key-encryption key (per environment), held entirely inside Azure Key
   Vault. Its private material is never fetched, held, or logged by the application; the
   application only ever calls Key Vault's `wrap`/`unwrap` operations against it, identified by a
   full key id including version.
2. **DEK** — one per **administration**, generated by the application (`os.urandom(32)`), wrapped
   by the KEK, and persisted only in wrapped (ciphertext) form. Rotation creates a new *version*
   of this row rather than mutating it in place, so old document blobs stay decryptable.
3. **Document content key material** — not a separate stored key at all: each document is
   encrypted directly with the tenant's (unwrapped, transient) DEK using AES-256-GCM, with a
   random 96-bit nonce per object and the administration id + key version bound in as additional
   authenticated data (AAD).

The unwrapped DEK exists only in process memory, for the duration of a single encrypt/decrypt
call — never cached across requests, never logged, never persisted.

### The tenant unit is the administration, not the organization

A firm organization holds many client administrations (PRD §5.1, §8.1). If the DEK were
per-organization, a firm's single key would cover every client's documents, and revoking it would
take out every client at once — the opposite of IAM-004's "revocation isolates one tenant." Keying
per-administration means revoking one client's key can never touch another client's documents,
even when both are managed by the same firm.

### Rotation has no downtime because only the wrapper changes

Routine rotation (`EnvelopeEncryptionService.rotate_key`, `scripts/rotate_annual_keys.py`)
generates a **new DEK version**, wraps it, marks it 'active', and retires the previous version —
it does not touch a single stored document. New writes use the new version; old objects stay
readable via the key version they were originally encrypted under. This is the entire reason
envelope encryption is worth the extra layer: rotating a tenant's key is a KMS wrap call plus two
small database row updates, regardless of how many documents that tenant has stored.

KEK rotation is a separate, system-wide event with its own re-wrapping sweep
(`EnvelopeEncryptionService.rewrap_after_kek_rotation`, `scripts/rewrap_after_kek_rotation.py`):
after the KMS key rotates to a new version, every administration's DEK still wrapped under the old
version gets unwrapped and re-wrapped under the new one, in place. No DEK value changes and no
document is touched — the sweep operates only on small wrapped-key rows, never on the (potentially
enormous) document/attachment blobs.

### Emergency rotation

Two distinct emergency paths, because the two things that can be "compromised" are different in
scope and remedy:

- **One tenant's DEK is suspected compromised** (a leaked wrapped-key dump, a credential that
  could unwrap for that tenant specifically): `scripts/emergency_rotate_key.py
  --administration-id <uuid>` runs the same `rotate_key` used for scheduled rotation, immediately,
  with `reason='emergency'`. This is honest about its limits: rotation prevents the old DEK from
  protecting anything *new* going forward, but does not retroactively un-expose documents an
  attacker already decrypted with the compromised key. If the tenant's existing documents
  themselves must be cut off, that's `revoke_key`, not `rotate_key` — see below.
- **The KEK itself is suspected compromised** (e.g., an over-broad Key Vault access policy):
  1. Rotate the KEK in Key Vault (creates a new current version).
  2. Run `scripts/rewrap_after_kek_rotation.py --old-kek-key-id <compromised-version>` to move
     every tenant's DEK onto the new version.
  3. Confirm the reported count is complete, then **explicitly disable** the old KEK version in
     Key Vault. Steps 1–2 alone leave the old version live and unwrap-capable — disabling it is
     the step that actually cuts off whoever had access.

`revoke_key` is the third, most drastic operation and is distinct from rotation entirely: it
deletes the wrapped DEK material outright (the database tombstones it — see the migration's
`administration_encryption_key_revoked_has_no_material` constraint), so every document that
administration ever stored becomes permanently unreadable, including by LEDGR itself. This is
IAM-004's guarantee exercised directly, and it is why revocation and rotation are separate
operations rather than one with a flag: rotation is routine and reversible in effect (old data
stays readable); revocation is neither.

### The one narrow cross-tenant role

The KEK re-wrap sweep and the annual rotation sweep are the first two operations in this system
that legitimately need to touch every tenant's key row in one pass. ADR-003 anticipated exactly
this and deferred it ("a fourth role for legitimate cross-tenant batch reads... belongs with the
JIT/approval tooling"); this ADR implements it as `ledgr_ops` — `BYPASSRLS`, but granted `SELECT`
on `administration` and `SELECT/INSERT/UPDATE` on `administration_encryption_key` only. It has no
access to any other table. Bypassing RLS is scoped by what it's granted, not by trust in the role
itself. Full JIT approval/audit wrapping around *when* `ledgr_ops` credentials get used remains
future work — flagged here, not solved here.

## Alternatives considered

| Option | Rejected because |
|---|---|
| One DEK per **organization** instead of per-administration | Defeats IAM-004 directly for the firm-led account model: a firm's single key would protect every client's documents, so revoking it — the whole point of a per-tenant key — would take out every client at once, not one. |
| One KEK per administration (full per-tenant HSM-backed keys) instead of one shared KEK wrapping many DEKs | Doesn't scale to NFR-010's 100,000 administrations — Key Vault has per-vault key limits and per-operation costs that make a key-per-tenant model impractical at that count. It also doesn't match SEC-022's own wording ("per-tenant data encryption **keys**" plural, wrapped by "**a** key-encryption key" singular), which already describes the envelope-encryption pattern chosen here. |
| Re-encrypt every stored document on each rotation, rather than versioning the DEK and leaving old objects under their original key | Directly violates SEC-023's "no downtime" requirement at any real document volume — re-encrypting a tenant's entire archive is neither instant nor safe to do transactionally. Versioned DEKs with lazy (never-required) migration of old objects is the standard, and only practical, envelope-encryption rotation pattern. |
| Store the wrapped DEK directly on each document row instead of a shared per-administration `administration_encryption_key` table | Would mean every document independently re-derives/duplicates the same wrap material and makes rotation an O(documents) operation instead of O(1) — exactly the downtime problem SEC-023 rules out. A single versioned key row per administration, referenced by version number from each document, is what makes rotation cheap. |
| Let ordinary tenant-scoped RLS (`ledgr_app` + `app.current_org_id()`) serve the rotation/re-wrap sweeps, one administration at a time in a loop, instead of a dedicated `ledgr_ops` role | Possible, but means impersonating every tenant in turn (spoofing session context for a batch job) rather than a job that is honestly cross-tenant by design — and it still wouldn't solve enumerating *which* administrations exist without another cross-tenant read. A narrowly-granted `BYPASSRLS` role scoped to exactly the two tables these jobs touch is more honest about what's actually happening and easier to audit. |
| A single AES-GCM key per document, itself wrapped by the tenant's DEK (three envelope layers instead of two) | Would add a wrap/unwrap KMS round trip — or at minimum a DEK-unwrap — per *document* rather than per rotation event, with no isolation benefit over binding the administration id and DEK key_version into the AAD the way this design already does. Rejected as unnecessary depth for the isolation property it would buy. |

## Consequences

- Document/attachment storage code (not yet built — this ADR covers the key-management layer
  only) must, when it lands, call `EnvelopeEncryptionService.encrypt`/`decrypt` and store the
  returned `key_version` alongside each blob, so the correct historical DEK version can always be
  found for decryption. This is a required integration point for that future work, not something
  this ADR builds.
- A brand-new administration must have `EnvelopeEncryptionService.provision_key` called in the
  same operation that creates it. The firm-bootstrap path
  (`app.create_firm_client_administration`) already does this atomically at the database level, by
  taking a pre-wrapped DEK as a parameter — wrapping happens in application code first, since a
  `plpgsql` function cannot call out to Key Vault. The self-managed signup path is an ordinary
  tenant-scoped insert and does not yet exist as a real endpoint; whoever builds it must call
  `provision_key` explicitly.
- `AzureKeyVaultKeyManagementService` is written against the documented Azure SDK surface but
  could not be exercised against a live Key Vault in this environment — there is no official local
  emulator for Key Vault the way Azurite emulates Blob Storage. `LocalDevKeyManagementService`
  fills that gap for local/CI use and is deliberately not selectable as a production
  configuration (see `api.config.Settings.kms_provider`).
- `ledgr_ops`'s existence means every future cross-tenant batch job (the NFR-033 nightly integrity
  job, ops reporting) has a role to extend rather than a reason to invent a new bypass — but each
  such extension should get its own narrow `GRANT`, not broader access to this role.
